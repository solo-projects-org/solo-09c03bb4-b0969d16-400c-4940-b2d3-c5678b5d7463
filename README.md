# 景区接驳车等待核查

按场次导入闸机 CSV（每分钟的入队人数、登车人数），求所有完整配对下“等待超过
15 分钟”的乘客人数上下界，判定整场是否多于 10 人；抽查有结果后可按凭证号补录
乘客的入队/登车分钟和人数，与已采信凭证共同重算。

新换的闸机按读头导出计数（每行：分钟号、读头号、人数，不带入队/登车方向），
本系统用“读头方向对照”把这种表换算成分钟表后再走同一套核查流程。

## 启动

```bash
docker compose up --build
```

浏览器打开 <http://localhost:8000>。SQLite 数据放在命名卷 `bus-wait-data`
（容器内 `/data/app.db`），删除容器不会丢数据。

本地直接运行（可选）：

```bash
pip install -r requirements.txt
DB_PATH=./data/app.db uvicorn app.main:app --reload
```

## 使用流程

1. **导入 CSV（按方向计数）**：三列，顺序为分钟号、入队人数、登车人数。支持带表头
   （`分钟号,入队人数,登车人数` / `minute,joins,boards`，列顺序可换）或不带表头；
   支持 UTF-8（含 BOM）和 GB18030。
   - 分钟号可任意起始，不必从 0 开始；单场跨度至多 120 分钟。
   - 表中未列出的中间分钟按“该分钟 0 人入队、0 人登车”补齐，导入成功后会明确提示。
   - 重复分钟号、负数、非整数、列数不对、超过 120 分钟、开场队列为负、
     散场队列不为空（全场入队≠登车）都会**整表退回**，不会留下半张表。
2. **人工核对**：场次页点“标记为已人工核对”。只有经人工核对的场次才能用作
   读头方向对照。
3. **建立读头方向对照**：在首页选一场已人工核对的场次，上传该场的读头表
   （三列：分钟号、读头号、人数；同一套读头至多 12 个，缺行按 0 人计）。
   每个读头的方向固定，**所有可行分法都须逐分钟还原该场次的入队和登车人数**；
   新对照无解就退回，原对照继续生效。新对照有解即取代原对照成为现行对照。
4. **导入读头 CSV**：上传新一场的读头表，读头须在现行对照中出现过。
   只有现行对照的**各可行分法换算出的分钟表完全相同**、且整场能配齐，
   才生成可导入的预览；否则整表退回并说明原因。
5. **确认建场**：预览页确认时按落库当时的现行对照复核——仍能唯一得出预览里的
   分钟表才按原核查流程建场；对照已变化导致复核不通过时不建场，需重新预览。
   已建场的预览再次确认时返回原场次，不会重复建场。
6. **查看结论**：场次页显示超时人数下界/上界、凭证锁定人数、匿名乘客区间和
   **达标 / 超标 / 待核**。
7. **补录凭证**：填写凭证号、入队分钟、登车分钟、人数。凭证乘客从该分钟的闸机
   人数中核销，剩余匿名乘客重新求上下界，总超时人数 = 凭证中确定超时人数 +
   匿名乘客超时区间。
   - 凭证分钟号必须在本场范围内，登车不早于入队，人数 ≥ 1。
   - 同一凭证号、同样内容重复提交：只计一次，结论与版本不变（API 返回 200，
     `outcome=duplicate`）。
   - 同一凭证号、内容不同：报冲突，拒绝覆盖（API 返回 409）。
   - 凭证人数超过该分钟闸机人数、或核销后剩余乘客配不齐：整笔退回（422），
     凭证和结论都不落库。
   - 并发补证在 `BEGIN IMMEDIATE` 写锁内“读全部已采信凭证 → 连同新凭证重算 →
     同事务写入”，后到者一定看到先到者已提交的凭证；重算期间网页/API 读到的是
     上一次已提交的结论（WAL 快照），不会看到半成品。

## 读头表怎么换算成分钟表

对照读头表与所选场次逐分钟对齐后，枚举每个读头的方向（入队/登车），凡能逐分钟
还原该场入队和登车人数的分法都是**可行分法**（读头至多 12 个，枚举量有限）。
现行对照保存全部可行分法。导入新读头表时，把每个可行分法分别换算成
（入队分钟表, 登车分钟表）：

- 换算结果互不相同 → 无法唯一确定方向，整表退回；
- 换算结果完全相同但整场配不齐 → 整表退回；
- 换算结果完全相同且能配齐 → 生成预览，确认后建场。

确认与建场在同一事务内完成：先按落库当时的现行对照重新换算并比对预览，
一致才建场，因此预览到确认之间对照被更换也不会落进错误数据。

## 判定口径

对一场数据，把“完整配对”理解为：每个登车名额分配给某个入队分钟不晚于该登车
分钟的乘客，全场恰好配完。乘客在分钟粒度上不可区分。于是超时人数不是单一值，
而是一个区间 `[下界, 上界]`：

- 上界 ≤ 10 → **达标**（怎么配都不会多于 10 人）
- 下界 > 10 → **超标**（怎么配都多于 10 人）
- 其余 → **待核**（取决于具体配对，需要更多凭证或现场记录）

等待时长 = 登车分钟号 − 入队分钟号，超过 15 分钟即计入。

### 上下界怎么算

两个按登车分钟升序的贪心，只按分钟聚合人数，单场最多 121 分钟，与乘客总数无关：

- **下界**：每次登车优先用未超时（入队于 `[b-15, b]`）且最早入队的乘客；
  没有未超时乘客时才动用已超时乘客中最早入队者。
- **上界**：每次登车只要有已超时乘客就先用其中入队最晚者（本次必超时）；
  否则用未超时乘客中入队最晚者，把更早入队、更接近过期的人留给后面。

`tests/test_matching.py` 把乘客和名额展开成个体、穷举全排列做交叉验证（阈值
0/1/2/3/5/15 各 250 组随机小数据），开发过程中另外用 3000+ 组随机数据和枚举
穷举核对过。读头方向分法枚举同样用 3000 组随机小数据与朴素逐掩码求和交叉验证。

### 凭证如何并入

凭证描述的是已经确定的乘客：他们的入队分钟、登车分钟和人数已知，等待时长也
确定。计算时先把这些人数从对应分钟的入队/登车人数里扣掉（核销），剩余匿名
乘客继续用上面的贪心求区间，最后把凭证中确定超时的人数加到区间两端。

“扣掉后仍能配齐全场”既保证凭证与闸机记录不矛盾，也保证能把这些凭证乘客与
匿名乘客拼成整场的完整配对；这也是保存新凭证的前提。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/health` | 健康检查 |
| GET | `/api/sessions` | 场次列表与结论 |
| POST | `/api/sessions` | 上传方向 CSV（multipart 字段 `file`），成功 201，退回 422 |
| GET | `/api/sessions/{id}` | 场次、结论、凭证、分钟明细 |
| POST | `/api/sessions/{id}/credentials` | 补录凭证，JSON：`credential_no`、`join_minute`、`board_minute`、`count` |
| POST | `/api/sessions/{id}/verify` | 标记为已人工核对（幂等） |
| GET | `/api/calibrations/current` | 现行读头方向对照（无则 `null`） |
| POST | `/api/calibrations` | 上传对照读头表（multipart：`session_id` + `file`），成功 201；无解/不合法 422，原对照继续生效 |
| POST | `/api/imports/preview` | 上传新场读头表（multipart：`file`），唯一且能配齐才生成预览（201），否则 422 |
| GET | `/api/imports/{id}` | 预览内容与状态 |
| POST | `/api/imports/{id}/confirm` | 按落库时现行对照复核建场：成功 201，已建场 200 返回原场次，复核不通过 409 |

网页表单使用同样的逻辑，提交后 303 重定向并显示中文提示。

## 示例数据

- `samples/meets.csv`：达标
- `samples/review.csv`：待核（下界 1，上界 11）
- `samples/exceeds.csv`：超标（下界 11，上界 16）
- `samples/reader_ref.csv`：`meets.csv` 同场的读头表（读头 1 入队、读头 2 登车），
  把 `meets.csv` 人工核对后用它建对照
- `samples/reader_next.csv`：下一场的读头表，建对照后可预览并确认建场
